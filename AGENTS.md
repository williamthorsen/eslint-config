# eslint-config monorepo

## Overview

Three published packages, of which `@williamthorsen/eslint-config-typescript` is the primary public artifact; `README.md` describes all three.

## Project structure

- `packages/typescript/`: `@williamthorsen/eslint-config-typescript`. Sources under `src/`, compiled to `dist/esm/`, with subpath exports beside the root entry. Custom ESLint rules live in `src/plugins/rules/`.
- `packages/strict-lint/`: `@williamthorsen/strict-lint`. Compiled to `dist/esm/`; ships a `strict-lint` bin. `bin/strict-lint.js` is committed rather than built: pnpm links a bin before anything compiles, so a `bin` naming a path under `dist/` fails to link on a fresh clone and never retries. The wrapper loads `dist/esm/bin/strict-lint.js` at runtime, and `__tests__/bin-targets.tool.test.ts` holds every workspace to the pattern.
- `packages/tsconfig/`: `@williamthorsen/tsconfig`. No build step; ships `tsconfig.base.json`, which inlines `@tsconfig/strictest`'s settings and adds the Node/build options that it omits, alongside a readyup kit. The repo root consumes it via the workspace symlink. `src/` is never built and never published: It exists so that the kit's predicates get tests and coverage.
- `eslint.config.ts` (repo root): imports `packages/typescript/src/` directly; needs no build.
- `.config/nmr.config.ts`: repo-level overrides for the `nmr` script runner.
- `.config/readyup.config.ts`: names the packages whose readyup kits check this repo.
- `.config/release-kit.config.ts`, `.config/v11y-check.config.json`: config for the corresponding tools invoked by GitHub Actions reusable workflows.
- `.config/wt.toml`: worktrunk's pre-start hooks, which run `direnv allow` and `pnpm install` in a new worktree before its creation completes.

## Commands

This repo runs on [`@williamthorsen/nmr`](https://www.npmjs.com/package/@williamthorsen/nmr); a bare `nmr` lists every command and the shell command to which it resolves, and `.config/nmr.config.ts` holds the repo-level overrides. Invoke it as `pnpm exec nmr`, never `npx nmr`, which inside a worktree can resolve an `nmr` from outside it. Scope follows the working directory: From the repo root a command fans out across every workspace; from a workspace directory it targets that package alone.

Iterate with `nmr check`, and run `nmr ci` before pushing. `nmr ci` adds a recursive build, `strict-lint` in place of `eslint`, coverage, and a fresh compile of both kits, so it is the slow gate rather than the inner loop. It is also the only one of the two that catches declaration-emit diagnostics, lint warnings, coverage shortfalls, and a stale kit bundle.

Releases are triggered via the **Release** GitHub Actions workflow (`workflow_dispatch`), which uses release-kit to bump versions, regenerate CHANGELOGs, and push tags. Tag pushes (`<workspace>-v<semver>`) then trigger the **Publish** and **Create GitHub Release** workflows. Don't push release tags by hand.

## Commit conventions

Commit titles are rendered by `describe-change.sh` from `commit.title_format` in `~/.agents/preferences.yaml` (currently `[{scope}|{type}: ]{title}`). Don't assemble titles by hand; invoke the commit skill, which calls the script. The project-specific values to pass are:

- **`--scope`:** `root`, `strict-lint`, `tsconfig`, `typescript`, or `*` for changes spanning multiple workspaces. Pass `typescript`, never the `ts` alias; `.config/release-kit.config.ts` resolves `ts` only so that the commits predating the switch keep resolving.
- **`--type`:** See the work-types table in `docs/versioning-and-changelog.md`. Append `!` after the type for breaking changes (e.g., `feat!`); `drop` always takes it.

Full reference: `docs/versioning-and-changelog.md`.

## Definition of done

Two workspaces ship a readyup kit. A change that alters anything a kit asserts is not done until that kit's `.readyup/kits/default.ts` reflects it and `rdy compile` has run in its own workspace. When the kit work does not belong in the same change, file a ticket for it before closing the one that prompted it.

- **`packages/typescript`** asserts a peer range, the projectService posture, the ESLint config conventions that a consumer is expected to follow, and the tsconfig prerequisites on which a TypeScript eslint config depends.
- **`packages/tsconfig`** asserts that every workspace tsconfig reaches the base, restates none of the options that it supplies, and runs on a Node major implementing its ES year. An edit to `tsconfig.base.json` changes what the kit reports, since the kit measures a consumer against the base's own settings.

Recompiling is the only thing that updates a bundle: The typescript kit inlines that package's peer ranges at compile time, so a peer bump leaves the committed bundle stale with neither recorded hash changing. A readyup upgrade is the same hazard from another cause, since the compiler stamps its own version into the bundle that it emits. Because a bare `rdy verify` compares the recorded hashes against the files on disk and sees neither case, `check:strict` runs `rdy verify --rebuild`, which compiles afresh and compares bytes. When it fails, recompile both kits with `pnpm --filter @williamthorsen/eslint-config-typescript --filter @williamthorsen/tsconfig exec rdy compile`.

## Gotchas

- **Hooks:** `lefthook` runs `nmr fmt` on staged files pre-commit and stages what it rewrites (see `lefthook.yml`).
- **A readyup kit spans two trees.** Its predicates live in the workspace's `src/readiness/`, where tests and coverage reach them; `.readyup/kits/default.ts` holds only the kit declaration and the filesystem wrappers into which it composes them, and `rdy compile` bundles the two. Putting a `__tests__/` under `.readyup/` instead would collect nothing, because tinyglobby does not traverse dot-directories: Vitest reports the files as zero tests rather than as an error. A kit's `export default` is required by readyup and is the only one that either workspace contains. `.config/readyup.config.ts` points two of its entries at this repo's own kits, `@williamthorsen/tsconfig` and `@williamthorsen/eslint-config-typescript`, so the sweep in the next bullet checks the repo against each of them. The latter's extends check matches the package specifier as text or a path into a workspace providing the package, which is what lets `eslint.config.ts` satisfy it by importing `packages/typescript/src/` directly.
- **`.config/readyup.config.ts` configures an advisory sweep that is run only by hand.** It names the packages and repositories whose kits check this repo against their own conventions, and `pnpm exec rdy run --sources` is the only thing that runs them: No workflow and no `nmr` command does. A `github:` source's kit is fetched at run time, so the sweep needs network access. `check:strict`'s `verify:kits` is a different subcommand, `rdy verify --rebuild`, covering only this repo's own two published kits. Run the sweep by hand when touching tooling or guidance.
- **Test helpers come from two toolbelt packages, and only half the convention is enforced.** `silenceConsole`, `listConsoleLines`, `throwOnProcessExit`, and `disposeOnTestFinished` come from `@williamthorsen/toolbelt.vitest/candidate`; `captureError` and `pointArgvAt` from `@williamthorsen/toolbelt.testing/candidate`. `packages/strict-lint` declares both, because the tests that import them live there. The `toolbelt.vitest` kit reports a hand-rolled process-exit mock, so the sweep above catches that one. Nothing reports a hand-rolled console capture or `process.argv` save-and-restore; for a new test file, this note is the only signal.
- **`nmr build` is a publishing step, not a prerequisite.** Lint, typecheck, and tests all read `src`. `nmr ci` still runs `build` first so that publish-path breakage is detected early. It is also the only command that clears `noEmit`, so no other check reports declaration-emit diagnostics (TS2883, TS4023, TS5011): A tree that cannot be published still passes `check:strict`.
- **Two Vitest configs serve the whole repo.** `vitest.config.ts` and `vitest.root.config.ts` each call the factory from `@williamthorsen/nmr/vitest`; packages have no config of their own, because Vitest walks up from the run root to find one. Because the root variant excludes `packages/**`, `nmr root:test` runs only root-level tests.
- **Test suites are selected by filename, not by config.** The shared config declares four projects named for the furthest thing that a test reaches: `*.tool.test.ts` is `tool`, `*.localhost.test.ts` and `*.remote.test.ts` name tiers in which this repo has no tests, and everything else under `__tests__` falls to the `unit` residual. `tool` means a process-scale tool (a linter, compiler, or spawned binary) reached as a process or through its own JavaScript API; both consumer packages declare `eslint` as a peer, so a test that constructs an `ESLint`, a `Linter`, or a `RuleTester` belongs there. Importing a peer for constants or types does not, and neither does mocking one out. Because `nmr test` runs `unit` and `tool` together by naming them rather than by negating the ones that it skips, a tier added in a later release is opt-in. Because `unit` is a residual and the shared config sets `passWithNoTests`, a missing or misspelt tier infix is silent in both directions: The file runs under `unit`, and a fan-out that reached nothing still reports success. Verify a tier change by the number of files that `nmr test:unit` and `nmr test:tool` each collect, never by a green run.
- **`tsconfig.base.json` inlines `@tsconfig/strictest` deliberately, and a root test holds it to that.** An `extends` cannot be reintroduced: Resolvers that don't realpath pnpm symlinks fail to follow the second hop, which is the bug that the inlining fixed. `__tests__/tsconfig-base.tool.test.ts` compares the inlined block against the installed devDependency in both directions, so bumping `@tsconfig/strictest` fails the suite whenever upstream's settings changed. Mirror the change into the base in the same commit as the bump, typed for the settings change rather than as `deps`: A strictness setting that upstream added or altered is consumer-visible, and `deps` would file it under a dev-only section. Splitting the two leaves an intermediate commit whose suite fails in either order.
- **Lint fixtures live in `packages/typescript/__fixtures__/`, outside `src`.** That keeps them out of test collection, coverage, and the published `dist`; four of them are deliberately named `*.test.*`, and ESLint ignores the whole tree because the fixtures violate the rules that they exercise.
- **A case handed to `createTypedRuleTester()` must typecheck under `packages/typescript/__fixtures__/rules/tsconfig.json`.** That fixture sets `types: []` and a `lib` of `ES2024` plus `ESNext.Disposable`, so a case that uses anything else -- a `node:` import, an ambient such as `console` -- resolves to nothing and typechecks as `any`, on which a type-aware rule returns early: The case passes while exercising none of the behavior that it names. `ruleTester.ts` registers an `every case typechecks` test per suite that compiles the cases and reports each offender with its diagnostic. Declare the shapes that a case needs inline, hoisting a shared fragment when several cases want the same one, as `no-floating-disposable` and `no-unused-map` do; widening the fixture's `lib` or `types` would reopen the hole. Suites built with a plain `RuleTester` are exempt, having no program to check against. The helpers live in `packages/typescript/src/plugins/rules/test-utils/`, outside `__tests__/`, which coverage excludes; they stay out of the published `dist` because `nmr-compile` emits only what the package's entry points reach, and nothing published imports them.
- **`*.rules.` names a rule-tester table, which the Vitest lint config skips.** These files declare their cases as a table handed to `RuleTester.run()`, which generates the `describe`/`it` blocks internally, so `@vitest/eslint-plugin` parses no test call in them: Its rules have nothing to act on, and `vitest/require-hook` reports the table itself as unhooked setup. Because the root config ignores `**/*.rules.*test.ts` rather than allowlisting tester variable names, a new custom rule needs no config edit; the single `*` spans zero characters, which is what lets one pattern cover a bare `*.rules.test.ts` alongside the `*.rules.tool.test.ts` that these files use. The `.rules.` infix does not select a suite; the trailing `.tool.` does, because only the infix immediately before `.test.ts` names a project. Keep hand-written Vitest assertions in a sibling file without `.rules.`, where the plugin's rules do apply; `no-unused-map` is split that way.
- **`strict-lint` and `typescript` import their own source through `#src/*`, declared twice.** The alias maps to `./src/*` in the package's tsconfig `paths`, which `tsc` consults first and `nmr-compile` rewrites to relative `.js` specifiers on emit, and in its `package.json` `imports`, which jiti (loading the root `eslint.config.ts`) and Node (running `strict-lint`'s bin from source in tests) need because neither reads `paths`. `__tests__/src-alias.tool.test.ts` holds the two declarations to the same mapping. An import of a file under `src/` never climbs with `..`: It is relative when its target is in the importing file's directory or below, and uses `#src/` otherwise; a test's single `..` to the directory beside its `__tests__/` is the one exception. `src/readiness/` and `.readyup/kits/` stay relative, because `rdy compile` bundles them with a fixed tsconfig rather than the package's own. The root tsconfig sets `rewriteRelativeImportExtensions: false`, since the option makes a `.ts` extension on a `#` specifier error TS2877; `nmr-compile` turns it back on for emit. A new compiled package needs both declarations and an entry in the per-package `import-x/resolver` blocks of `eslint.config.ts`, and its name added to `aliasedPackages` in the alias test; Vitest resolves the alias through `tsconfigPaths` in `vitest.config.ts` without per-package wiring.
